
只查看界面时，在**本地开发地址**后加 `?preview=1`：

- `/index.html?preview=1`：虚构名单，可增删明细并检查填写，不能提交。

示例模式仅在本机开发服务器生效，生产构建不包含示例数据，不会因网址参数开启。

## 连接 Supabase

以下步骤保留用于新环境安装或重建。当前项目已完成数据库与34人名单导入、管理员账号创建及指定管理员授权，并已通过本地后台登录、真实填报和四类导出的完整验收，无需重复导入现有名单或重复授权。当前收集保持关闭，待远程部署和正式网络验证完成后再开放。

1. 登录 Supabase，创建项目，选定组织、项目名和地区。数据库密码由项目所有者设置并保管，不放进网站。
2. 在 SQL Editor 新建查询，执行 `private/setup.sql` 全文，即可一次初始化结构及34人名单，默认保持收集关闭。此文件含真实姓名，勿公开。通用结构脚本是 `supabase/schema.sql`，单独名单脚本是 `private/roster-import.sql`；脚本可重复执行，不覆盖已有数据。
3. 在项目的 API 配置页面取得 **Project URL** 和 **Publishable key**。网页只需要这两项公开连接配置；不要使用 secret key、service_role key、数据库密码或访问令牌。
4. 复制 `.env.example` 为 `.env.local`，填入 URL 和 publishable key。批次ID保持默认，除非另建了新收集批次。重新启动开发服务器。
5. 在 Authentication / Users 建立管理员的邮箱密码账号。账号密码由本人设置；记录该用户的 UUID。
6. 在 SQL Editor 中执行下面的授权，将占位字符串替换为该用户的真实 UUID：

```sql
insert into h41.admins(user_id)
values ('替换为管理员的Auth用户UUID')
on conflict(user_id) do nothing;
```

7. 打开 `admin.html` 用该邮箱密码登录。在“基础设置”核对已导入的名单和两类范围；已执行第2步时，无需再次导入名单。仅在新环境尚无名单时补充导入。若重名，为显示名添加班内可辨认的区分，内部学生ID不会改变。部署和验证准备完成后，再开启收集。
8. 生产地址确定后，在 Supabase Auth 的 URL Configuration 设置 Site URL，并只添加实际需要的 Redirect URL。本版使用邮箱密码登录，不使用注册、邀请、邮件链接或第三方登录。可在 Auth 设置中关闭公开注册；即使普通用户拥有账号，服务器也不会授予管理权限。

真实名单、填报结果和测试导出文件放 `private/` 或 `exports/` 等已忽略目录，不提交到公开代码仓库。管理员密码不进入前端构建或日志。浏览器中的管理员会话只保存在当前标签页的 sessionStorage。

## 使用后台

- **填报进度**：查看未填名单、最近有效提交时间；下方可整理原始提交。改姓名会整体移动这份提交的全部明细。
- **活动统计**：五类人数、总参与人数和活动明细。按姓名或类别筛选；导出按钮导出全部有效明细，与筛选无关。
- **获奖清单**：按姓名筛选、按年月排序，统计个人获奖人数及明细条数；团队奖由多位同学填报时，各保留一条个人记录。
- **基础设置**：标题、两类范围、名单、收集开关。将成员排除后保留原记录，统计和正常导出不再计入；重新纳入即可恢复计算。

“整理”中的编辑、作废、恢复会原子处理同一人同一事项的全部重复原始记录。整份提交作废后，其明细退出统计；请先恢复原提交，再恢复或编辑因它失效的明细。不会物理删除历史记录。

学生遇到超时后，当前填写被保留并暂时锁定。点击“重试同一份填写”使用相同请求编号，服务端返回原回执或完成保存，不产生第二份记录。开始新的填写会生成新请求编号。手机刷新或关闭页面不会保留未提交的草稿。

## GitHub Pages 发布与维护

公开仓库及 Pages 配置已完成，首次 CI 部署结果待核验。后续按以下方式维护；前三项仅在重建环境时需要重新配置：

1. 创建 GitHub 仓库并将本“统计问卷”目录关联远程。仅提交源码、PRD和部署说明。
2. 在仓库 Settings / Secrets and variables / Actions / Variables 配置 `VITE_SUPABASE_URL`、`VITE_SUPABASE_PUBLISHABLE_KEY`，可选配置 `VITE_COLLECTION_ID`。这三项本来就会出现在浏览器中，不能填管理密钥。
3. 在 Settings / Pages 把 Source 设为 GitHub Actions。
4. 上一级 `.github/workflows/pages.yml` 会在推送 main 时运行测试、构建并部署 `site/dist/`，也可手动触发。
5. 确认 Actions 测试、构建与部署成功后，核验正式填写地址和后台登录；校园网、手机流量需由用户实际测试。确认名单、范围和访问正常后，在后台“基础设置”开放收集，再将链接发到班内。

班内时间提示是首页的普通文字；若后续调整，修改 `index.html` 的提示后重新构建。统计范围可直接从后台修改，无须重新部署。

## 数据与权限实现

所有业务表位于私有 `h41` schema，开启RLS且不给匿名/普通登录角色表权限。公开RPC只读取填写说明及有效名单，或校验并保存当前请求。管理RPC逐次核验 `auth.uid()` 是否在 `h41.admins` 中；不存在“登录就能读取全班数据”的路径。

写操作使用数据库事务并按收集批次行加锁；服务端执行长度/数量/类别/月格式/名单/开关校验。每份原始请求独立留存，管理员修改资料不改变幂等比较依据。导出与页面共用 `src/domain.js` 的有效记录规则。

技术依据：[Supabase 数据库函数](https://supabase.com/docs/guides/database/functions)、[行级权限](https://supabase.com/docs/guides/database/postgres/row-level-security)、[认证](https://supabase.com/docs/reference/javascript/auth)、[GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/about-github-pages)。
